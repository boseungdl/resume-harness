# 용량 산정 (Capacity Estimation) — 워크로드로 인프라 스펙 정하기

> 2026-08 지게차 포폴 정리 중 학습. "설계 기준: 일 100만 이벤트 / 30fps → 33ms 예산" 같은 숫자가 나오는 과정.

## 0. 큰 그림

> **내 짐(수요)을 재서, 부품 성적표(공급)와 같은 단위로 맞춘 뒤, 나눗셈으로 판정한다.**
> 수요는 계산하고, 공급은 조회하고, 조회 안 되는 것만 측정해서 만든다.

---

## 1단계. 워크로드 재기 — 질문 3개

| 질문 | 구하는 법 | 디테일 |
|---|---|---|
| 한 개 크기 | 샘플 재기 `len()` | 바디만. 압축은 샘플 압축해 ÷상수(gzip ÷5~10, JPEG ÷20, H.264 ÷100). 페이로드 수십 바이트면 포장 몫 ×2 |
| 초당 건수 | 하루 건수 ÷ 10만 초 | 86,400 ≈ 10만으로 암산 |
| 보존·동시 | 요구사항에서 | 보존 기간 × 복제 벌수(보통 ×3), 동시 접속(전형: DAU의 1~10%) |

전형 크기: 로그/이벤트 1건 ≈ 1KB · 썸네일 10~100KB · 사진 수 MB · 720p 원본 프레임 2.7MB(1280×720×3B)

---

## 2단계. 수요의 세 축 — 각 축이 다른 자원을 때린다

```
① 양(바이트)  = 크기 × 건수      → 대역폭 · 디스크 용량
② 건수(횟수)  = 그 자체          → CPU · IOPS · 커넥션   (건마다 고정비)
③ 상주(머묾)  = 동시 수 × 개당    → 메모리
```

**② 건수는 곱셈 재료가 아니라 독립 축이다.** 요청 한 건엔 크기와 무관한 고정비(연결 처리·파싱·트랜잭션·디스크 IO 횟수)가 붙는다. 1KB×1만 건이 10MB×1건보다 힘든 이유. 작은 메시지가 많은 시스템(이벤트·IoT·채팅)은 바이트보다 건수에서 먼저 터진다. 대응책은 "묶기" — Kafka 배치, HTTP 연결 재사용 = 고정비를 여러 건이 나눠 냄.

### 축별 계산 디테일

**① 양 → 대역폭·디스크 용량**
- 대역폭: MB/s로 계산 후 **×8 해서 Mbps로** (회선 스펙이 비트 단위)
- 디스크 용량: 초당 흐름량 ×10만 = 일당 → ×보존일 ×복제

**② 건수 → CPU·IOPS**
- CPU 스펙엔 "초당 몇 건"이 없다 (내 코드에 달렸으므로). 다리를 놓는다:
  - 1건당 CPU 시간을 측정/전형값으로 확보 (단순 API 1~5ms, 이미지 추론 수십 ms)
  - `코어 1개 처리량 = 1000ms ÷ 1건당 ms` → `필요 코어 = 초당 건수 ÷ 코어당 처리량`
- 디스크는 용량과 별도로 **속도(IOPS·MB/s) 칸을 따로 확인** — 용량 남는데 속도에서 터지는 경우가 흔함

**③ 상주 → 메모리**
```
머무는 것 목록(연결·세션·캐시·로드된 모델) → 개당 크기(전형값→측정) → 동시 수 → 합산
개당 크기 측정법: 1,000개 접속시켜 늘어난 메모리 ÷ 1,000
고정 상주 잊지 말 것: 런타임, ML 모델(그 자체로 수 GB)
```

---

## 3단계. 안전계수

**피크 ×2~3, 성장 ×10.** 평균으로 설계한 시스템은 피크에 죽는다.

---

## 4단계. 비교 — 짝 맞춘 나눗셈

공급은 정하는 게 아니라 **조회**: 클라우드 카탈로그, 스펙시트, 공개 벤치마크. 내가 만든 것만 직접 벤치마크.

| 수요 (2단계 산출) | 카탈로그 짝 칸 | 예 |
|---|---|---|
| Mbps | "네트워크 성능" | 240M/5G = 0.05 → 여유 |
| 필요 코어 | "vCPU" | 4/8 = 0.5 → 적정 |
| GB + MB/s·IOPS | "용량 · 처리량" | 1.0 → **병목!** |
| GB (상주) | "메모리" | 0.3 → 여유 |

판정: **0.1 이하** 여유(과잉설계 금지) · **0.5~0.7** 임박(증설 계획) · **1 이상** 불가(스케일업 또는 구조 변경: 분산·압축·캐시·묶기)

**1에 가장 먼저 닿는 축이 병목. 돈과 설계는 병목에만 쓴다.**

---

## 5단계. 계산으로 방향, 측정으로 확정

- 계산은 **자릿수(10배 단위)만** 믿는다. 산출물은 "어디가 먼저 터지나"라는 방향.
- 확정: 부하 테스트(k6·locust·wrk) — 최대 처리량, p95 지연, 연결 수 대비 메모리 곡선
- 계산과 실측이 10배 이상 어긋나면 가정(1건당 CPU·개당 메모리)이 틀린 것 → 그 가정만 실측으로 갈아끼우고 재계산

---

## 6단계. 함정

1. **b ≠ B** — 회선은 비트, 데이터는 바이트. 1Gbps = 125MB/s. ×8 잊으면 8배 낙관.
2. **자원은 70%가 실질 한계** — 평균 90% 사용은 여유가 아니라 증설 시점.
3. **큰 건 몇 개보다 작은 건 왕창이 무섭다** — 건수 고정비. 총 바이트 같아도 건수 많은 쪽이 힘듦.
4. **평균이 아니라 피크로 설계.**
5. **메모리는 스톡, 나머지는 플로우** — 흐름 공식에 메모리 넣으면 틀림.
6. **과잉 정밀은 아마추어 신호** — 몇 % 오버헤드는 자릿수를 못 바꾸니 버림. 안전계수가 흡수.

---

## 외울 기준값 (공급 성적표)

- 1Gbps = 125MB/s · SSD 순차 수백 MB/s · 서버 1대 단순 요청 수천~수만/s · Kafka 수십만 msg/s
- 하루 ≈ 10만 초

---

## 내 프로젝트 대입 (면접용)

- **광고레이크**: 1KB × 일 100만 ÷ 10만 초 = **초당 ~12건** → Kafka 대비 1/10,000 → "스트리밍 과잉설계를 피하고 마이크로배치 선택". 100배 성장해도 1,200건/s — 재설계 불필요. 포폴 헤더 "일 100만→1억 / 1GB→100GB"가 이 계산의 산물.
- **지게차**: 입력 30fps → **프레임당 처리 예산 33ms** — 경량 모델(YOLO11n)·프레임 스킵 선택의 근거. 영상 출력은 MJPEG ≈ JPEG 100KB × 30fps ≈ **24Mbps/시청자** → 내부망 소수면 감당, 시청자 늘면 미디어 서버(WebRTC/H.264, 1~2Mbps)로 분리. 병목은 네트워크가 아니라 GPU 추론.

---

## 최종 한 문장

**양·건수·상주 세 축으로 수요를 재고(각각 대역폭·CPU/IOPS·메모리를 때린다) → 피크·성장을 곱하고 → 조회한 공급과 나눠 1에 먼저 닿는 축(병목)에 설계를 쓰고 → 자릿수는 계산으로, 확정은 부하 테스트로.**
