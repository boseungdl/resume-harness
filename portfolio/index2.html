01 Bronze 확장성 : 파티션 기준을 발생 시간에서 수집 시간으로
파티션 기준을 발생 시각에서 수집 시각으로 바꿔, 늦게 온 데이터도 그날 파티션 한 곳에만 쌓이게 했습니다. 처음 발생 시각으로 잡았을 땐, 전환이 최대 30일까지 늦게 오면서 오늘 도착분이 과거 날짜 파티션 수십 개로 흩어졌습니다. 최근 파티션만 봐선 새 데이터를 못 챙기고 과거까지 다시 훑어야 했는데, 수집 시각 기준에선 도착분이 발생일과 무관하게 그날 raw_date에 모여, 과거 파티션은 다시 건드릴 일이 없고 정제 때도 최근 파티션만 읽어 스캔을 줄일 수 있는 구조가 됐습니다. 발생 시각은 event_timestamp로 남겨 Silver 분석에서 사용했습니다.빠르게 받아내는 게 raw의 일이지만, 쌓는 방식 하나가 정제의 부담까지 바꿨습니다.
02 Silver 비용 최적화 : 스몰 파일 병합으로 조회 비용 절감
조회 비용을 줄이려고 스몰 파일을 주기적으로 병합했습니다. Silver는 매시간 증분 MERGE로 갱신돼 늦은 전환이 여러 파티션에 소량씩 쌓이고 MOR 특성상 delete 파일까지 늘어, 그대로 두면 조회 때 LIST·GET·메타 파싱이 파일 수만큼 불어납니다. 그래서 rewrite_data_files로 128MB 단위로 병합하고, 스냅샷 만료·고아 파일 정리도 같은 유지보수 배치로 함께 돌렸습니다. 스캔을 건너뛰는 프루닝은 Iceberg가 파티션·파일 통계로 해주는데, 파일이 잘게 흩어지면 파일별 min/max 범위가 겹쳐 잘 걸리지 않습니다. 병합으로 파일을 정돈해 그 프루닝이 제대로 먹히게 하는 게 제 몫이었습니다.저장 구조를 정할 땐 쓰는 속도만이 아니라, 읽는 비용도 같이 봐야 했습니다.
03 Silver 정합성 : 중복 유입에도 결과를 하나로
재처리해도 전환 수가 흔들리지 않도록, 중복을 단계별로 흡수하는 멱등 구조로 설계했습니다. 전환은 CVR·CPA로 이어지는 광고비 판단의 핵심이라, 한 건이라도 부풀면 예산 결정이 틀어집니다. 그런데 Kafka가 at-least-once라 재기동·재시도 때 같은 event_id가 다시 들어와, 그대로 집계하면 전환이 실제보다 많게 잡힙니다. checkpoint 오프셋 커밋은 유실만 막을 뿐 이 중복은 못 막습니다. Bronze는 원본을 손대지 않고 그대로 받는 계층이라 중복을 여기서 거르지 않고, 정확성은 Silver에서 흡수하기로 했습니다. raw에 같은 event_id가 여러 벌 쌓이면 그대로 MERGE할 때 한 타깃 행에 여러 소스가 부딪혀 실패하므로, 조립 땐 ingest_ts로 event_id별 최신 한 건만 남겨 소스를 유일하게 만든 뒤 event_id로 MERGE했습니다. 없으면 새로 넣고 있으면 그 행을 갱신하니, 몇 번을 다시 돌려도 결과가 같습니다(멱등). MERGE는 신규 INSERT와 지연 UPDATE를 태스크로 나눠, 어느 쪽이 어긋나는지 Airflow에서 바로 보고 실패한 쪽만 재시도하게 했고요.중복은 원천 봉쇄하기보다, 몇 번 들어와도 같은 결과가 되게 흡수하는 게 현실적이었습니다.

핵심 과제 · 해결
검출: 오탐을 지우면 진짜를 놓치는 문턱 딜레마
오탐을 지우면 미탐이 늘던 검출 딜레마를, 문턱을 역할별로 나눠 해결했습니다. 처음엔 검출 확신도(conf)를 0.5까지 올려 트럭·상자를 지게차로 잡는 오탐을 지우고 중복 박스도 NMS iou 0.7→0.45로 합쳤는데, 이번엔 회전하거나 가려진 순간 확신도가 떨어진 진짜 객체까지 걸러져 놓쳤습니다. 그래서 입구 conf는 0.3까지 다시 낮춰 약한 검출도 일단 트래커로 넘겼습니다. 이미 추적 중인 객체는 track_low_thresh 0.01로 아주 흐린 검출로도 같은 ID를 유지해 가림 순간에도 놓치지 않게 하고, 새 객체 등록만 new_track_thresh 0.65로 엄격하게 갈랐습니다. 0.65를 넘겨 후보가 돼도 바로 다음 프레임에 다시 잡혀 매칭돼야 정식 트랙이 됩니다(DeepSORT가 n_init=3으로 두는 연속 확인 관문이고, BoT-SORT는 2프레임 고정입니다). 진짜 객체는 화면에 수십 프레임 계속 있으니 이 관문을 자연히 통과하고, 한두 프레임 반짝하는 오탐은 여기서 걸러집니다. 놓치지 않으면서 오탐도 뜨지 않는 검출로 안정화했습니다.
추적: 회전·가림마다 ID가 바뀌는 ID 스위칭
회전하거나 가려질 때마다 같은 지게차에 새 ID가 붙던 ID 스위칭을, 매칭 성공률을 높여 잡았습니다. 원인은 매칭 실패였습니다. 트래커는 "예측한 위치와 새 검출이 겹치는가"로 같은 객체를 이어가는데, 가려지면 검출이 사라지고 회전하면 박스 모양과 확신도가 무너져, 짝을 못 찾은 검출이 새 ID를 받았습니다. 트래커부터 바꿨습니다. 흐려진 저신뢰 검출을 버리는 DeepSORT에서, 그걸 2차 매칭으로 재활용해 트랙을 잇는 ByteTrack으로 옮겨 회전·가림의 끊김을 줄였고, 외형 매칭(ReID)까지 얹을 수 있는 BoT-SORT로 정착했습니다. 그 위에서 match_thresh를 0.6→0.9로 올려 덜 겹쳐도 같은 객체로 인정하게 했고, 잠깐 사라진 트랙은 Lost로 보관하며 칼만 예측으로 위치를 이어가다 재등장하면 같은 ID로 복구시켰습니다. 보관을 길게 두면 유령 박스가 남아 track_buffer는 10프레임으로 줄였고, 재등장 위치가 예측과 어긋난 객체는 ReID로 생김새를 대조해 재확인했습니다. 그 결과 회전·가림을 지나도 ID가 유지돼 속도와 위험도 계산이 끊기지 않았습니다.

공개 고장 데이터도 믿을 센서도 없는 학습 데이터 부재
공공데이터(딸기 환경)에 펌프곡선·저항 물리식을 결합해 45종·90일 학습셋을 직접 합성하고, 정상만 학습해 재구성 오차로 이상을 잡는 비지도 AutoEncoder로 풀었습니다. 펌프 막힘은 공개 고장 데이터가 없어 지도학습이 불가능했고, EC·pH 센서는 오염·노후로 막힘을 수 시간~수 일 늦게야 드러냈기 때문입니다. 그래서 유량·압력·전류의 관계 파생 변수(전류 대비 유량 효율·압력 변화율·system_resistance)를 설계해 물리 지표만으로 전조를 포착했습니다. 펌프 사양은 임의로 지어낸 값이 아니라 국내 시설원예용 양액공급기(3마력·2.2kW급)를 참고해 정상 운영점(유량 78 L/min)을 잡았고, 무유량 대비 운영압 비율·효율까지 원심펌프 표준에 맞춰 물리적 자기일관성을 확보했습니다.
변수 45종을 한 모델에 넣자 생긴 도메인 노이즈 간섭
모터·유압·양액·구역 4개 도메인으로 분리해 정확도를 올리고, 이상의 원인까지 도메인·신호 단위로 짚었습니다(RCA). 45종을 한 AE에 다 넣으면 도메인 간 노이즈가 간섭해 정확도가 떨어지고 원인도 못 짚었기 때문입니다. 도메인별로 오탐을 추적하니 94%가 양액 한 곳에 몰려 원인 지점을 특정했고, 특정 막힘 1건에서는 누수 관련 신호가 이상 점수의 82%를 차지함을 정량으로 보여 판단 근거까지 설명했습니다.
라벨 없는 검증과 운영 오탐에서의 신뢰성 확보
'가짜 고장'을 독립 seed·4유형 16건으로 주입해 정직하게 측정한 결과, 검출은 단일센서 기준선과 동등하면서(막힘 100% 검출) 오탐률을 3.1%→1.8%로 약 1.7배 낮췄습니다. 고장 라벨이 없어 held-out으로 측정했고, 운영에선 정상 분포 기준 동적 임계값으로 계절·시간 드리프트에 대응했습니다. 위험은 실시간·평상은 10분 평균으로 부하와 오탐을 낮추고, 비운전·기동 구간은 펌프 상태 필터로 제외해 오탐을 원천 차단했습니다.

Log-Land · 이미지 메타데이터 기반 기록 플랫폼
개발
서비스 개요
사진 EXIF 메타데이터(시간·위치)를 읽어 지도·타임라인에 추억을 자동 기록하는 클라우드 다이어리입니다.
내 역할
CI/CD · GitOps. 배포 과정을 자동화하려고 CI/CD 파이프라인을 직접 설계했습니다.
PR→main 머지트리거→ GitHub Actions테스트·Build·ECR Push→ Kustomizeimage tag commit→ ArgoCDEKS 동기화·Slack 알림
요구사항
PR 머지 한 번으로 EKS까지 자동 배포 (GitOps)
처음엔 GitHub Actions에서 kubectl로 클러스터에 직접 배포(push)하면 충분하다고 봤습니다. 그러나 자격증명을 CI에 보관해야 하는 보안 부담과 배포 이력·롤백이 코드와 따로 노는 점을 가볍게 본 게 잘못된 판단이었습니다. 이후 ArgoCD GitOps(pull)로 전환해, Actions는 이미지 Build·ECR Push·Kustomize image tag commit까지만 맡고 실제 동기화는 ArgoCD가 Git 상태를 보고 수행하도록 역할을 분리했습니다. 그 결과 배포 상태가 항상 Git과 일치(선언적)하고 롤백은 revert 한 번, 자격증명은 클러스터 안에만 남아 보안과 재현성을 함께 확보했습니다. 자동화는 '돌아가게'가 아니라 '안전하게 추적·복구되게' 만드는 것이라는 걸 배운 작업이었습니다.
업로드 폭주에도 Pod OOM 없는 안정 운영
이미지 업로드가 몰리자 Pod가 메모리 임계를 넘겨 OOM으로 재시작을 반복했습니다. 처음엔 리소스 스펙만 키우면 끝이라 판단했지만, 정작 '터지기 전에 알아챌 장치'가 없다는 게 더 근본적인 문제였습니다. CloudWatch로 메모리 사용률 알람(Slack 연동)을 걸어 임계 도달 전에 통지하고, 리소스 request/limit과 노드 스펙을 함께 조정했습니다. 덕분에 사후 대응에서 사전 감지로 운영 방식이 바뀌어 같은 장애가 재발하지 않았습니다. 증상에 스펙으로 대응하기 전에, 무엇이 일어나는지 관측할 수 있어야 한다는 걸 체감했습니다.

서비스 개요
신용정보가 아닌 청년의 미래 소득 가능성을 평가해 투자하는 금융 플랫폼입니다. 고정 원리금이 아닌 예상 수익 비례 상환으로 청년 자립을 돕고, 청년↔기업 ESG 선순환을 설계했습니다.
내 역할
핵심 백엔드를 담당해 소득 추정 파이프라인(스펙 정규화 → LLM → 현가 할인)과 인증/인가(JWT·Redis)를 직접 설계·구현했습니다.

트러블 슈팅
비정형 스펙을 LLM에 그대로 넣자 생긴 추정 편차
자격증·경력 같은 비정형 스펙을 LLM에 바로 넣으면 연차별 소득 추정이 일관되지 않았습니다.→Perplexity로 스펙을 정규화(Batch)한 뒤 프롬프트 LLM으로 연차별 예상 소득을 생성하고, 인플레이션 현가 할인으로 최종 투자금을 산출하는 파이프라인으로 정리했습니다.
JWT는 로그아웃해도 유효해 탈취 시 악용 위험
JWT는 stateless라 로그아웃해도 만료 전까지 유효해, 탈취되면 그대로 악용될 수 있었습니다.→로그아웃된 토큰을 Redis 블랙리스트에 올려 검증 단계에서 차단하고, 만료 시간과 동기화해 자동 정리되도록 무효화했습니다.
계약서·명세서 건별 수기 작성에 따른 서식·금액 오류 위험
투자 계약서·상환 명세서를 건건이 수작업으로 만드는 건 불가능했고 서식·금액 오류 위험도 컸습니다.→iText로 사용자·계약 데이터를 채워 계약서/명세서 PDF를 자동 생성해 심사·정산 흐름에 연결했습니다.

댕동 · 반려견 동반 여행 플래너
개발
서비스 개요
반려견과 여행을 떠나는 사용자를 위한 맞춤형 여행 플래너로, 일정을 계획하고 여행 기록·포토카드로 추억을 남깁니다. 반려동물 산업 성장이 배경, 기존 숙소 예약 위주 서비스와 달리 여행 일정 계획 + 동행자 관리로 차별화했습니다.
내 역할
6인 팀에서 게시판/커뮤니티를 담당해 게시글·댓글 CRUD(MyBatis postMapper)와 이미지 업로드(S3)를 직접 구현했습니다. 데일리 스크럼·KPT 회고·WBS로 팀 진행을 관리했습니다.
FEHTML · CSS · JS · JSP BESpring MVC · MyBatis · MySQL 기능WebSocket · AWS S3 · Kakao/Google OAuth
트러블 슈팅
게시글 목록에서 댓글을 건건이 조회하는 N+1 쿼리
목록에서 게시글을 불러올 때 댓글·댓글 수를 게시글마다 따로 조회해 1+N개의 쿼리가 나갔고, 글이 쌓일수록 목록 응답이 선형으로 느려졌습니다.→MyBatis resultMap으로 게시글↔댓글을 조인해 한 번에 매핑하고 목록에 필요한 컬럼만 select하도록 정리, 쿼리를 1회로 줄여 목록 진입 응답을 안정화했습니다.
이미지를 DB에 직접 저장해 생긴 용량·조회 성능 저하
초기엔 업로드 이미지를 DB에 직접 넣었더니 테이블 용량이 빠르게 커지고, 게시글 조회마다 큰 바이너리를 함께 읽어 느려졌습니다.→원본은 AWS S3에 저장하고 DB에는 S3 URL·파일명·크기 등 메타데이터만 두어, 조회는 메타데이터만 읽고 이미지는 S3에서 직접 서빙하도록 분리해 DB 부하·용량을 동시에 줄였습니다.
팔로우·좋아요의 다대다 관계에서 중복·정합성 깨짐
팔로우(사용자↔사용자)와 좋아요(사용자↔게시글)를 단순 컬럼으로 처리하려다 중복 행과 집계 정합성 문제가 생겼습니다.→각각 연결(중간) 테이블로 분리하고 (from·to) 복합 유니크 제약으로 중복을 차단, 팔로잉/팔로워·좋아요 수 집계 쿼리까지 단순해지고 무결성을 확보했습니다.
