# 광고 데이터 레이크하우스 — 전체 프로세스·동작·설계 정리

> 코드(`iceberg-lakehouse-lab`) 기준으로 확정한 내용. 개념 설명이 아니라 "실제로 어떻게 도는지 + 왜 그렇게 설계했는지"를 정리.

---

## 0. 한눈에

```
[Criteo CSV] → kafka_producer(3토픽) → Kafka
   → Spark Structured Streaming(3잡) → Bronze(raw parquet, 수집시각 파티션)
   → [매시간] Silver 정제(dedup + JOIN + MERGE) → processed_events(Iceberg, MOR)
   → [매시간] Gold 집계 → campaign_summary(CTR/CVR/CPA)
   → Athena/QuickSight 조회
```

- 설계 기준(직접 정의): 일 100만 → 1억 이벤트(초당 ~12 → ~1,200), 일 ~1GB → ~100GB
- 실데이터: Criteo 30일 ≈ 1,640만 행(≈일 55만), 실습 샘플 100만
- 3대 설계 관점: **확장성 / 비용 최적화 / 정합성**

---

## 1. Bronze 적재 (수집)

**동작**
- `kafka_producer.py`: 결합 CSV 한 행을 **impression / click / conversion 3개 이벤트로 분리**해 각 토픽에 발행. 셋 다 같은 `event_id`(`evt_00000001`).
  - impression 즉시 / click 1~30초 뒤 / conversion 원본 지연(시간~일) 뒤
- `kafka_to_raw_files.py`: event-type별 **3개 스트리밍 잡**이 Kafka→raw parquet 적재.
  - `outputMode("append")`, `partitionBy("raw_date","raw_hour")` = **수집 시각 파티션**
  - `checkpointLocation`에 **Kafka offset 커밋** → 재기동 시 유실 없이 이어받음
  - 레코드에 `kafka_partition·offset·ingest_ts·event_timestamp` 기록
  - 트리거·maxOffsetsPerTrigger 미설정 → **기본(배치 끝나면 곧바로 다음), 배치 크기 상한 없음**

**설계**
- 파티션 기준을 **발생 시각이 아닌 수집 시각**으로: 전환이 최대 30일 늦게 와도 과거 파티션에 흩어지지 않고 그날 `raw_date` 한 곳에만 쌓임 → 과거 파티션 불변, 최근 파티션만 읽는 증분의 발판.
- Bronze는 **원본 보존 계층** — 중복이든 뭐든 손대지 않고 그대로 받음. 정확성은 Silver에서.

## 2. Silver 정제 (조립·정합) — `ad_lakehouse_silver` DAG (매시간 `0 * * * *`)

**DAG 순서**
```
check_raw → insert_new → update_late → compact → rewrite_deletes → expire → orphan(일요일)
```

**정제 job (`raw_to_processed_iceberg.py`) 데이터 흐름**
1. **read_zone**: `raw/{zone}/raw_date=*/raw_hour=*` glob → 각 존 **전체** 읽기(현재는 증분 아님). DataFrame(메모리 테이블) 3개.
2. **dedup (`latest_per_event`)**: 존별로 `Window.partitionBy(event_id).orderBy(ingest_ts desc)` → `row_number()==1`. 같은 event_id 여러 줄 중 **최신 1건만 선별**(삭제 아님). at-least-once 중복 제거.
3. **LEFT JOIN**: impression을 base로 click·conversion을 `event_id`로 이어붙임. 있으면 1·없으면 0 플래그(`click`, `conversion`). `event_date = to_date(imp_event_ts)`(=노출 시각).
   - 조인은 인덱스가 아니라 **broadcast hash join**(작은 쪽을 조인 시점에 해시테이블로 만들어 큰 쪽을 훑음). 크면 shuffle join.
4. **window 필터**: `event_date >= current_date() - 7 DAYS` (merge window 7일).
5. **쓰기 (2 태스크로 분리)**:
   - `insert_new` (mode=insert): `LEFT ANTI JOIN target` → target에 없는 event_id만 **INSERT**
   - `update_late` (mode=update): `MERGE INTO ... WHEN MATCHED AND (새 conversion/click) → UPDATE`
   - (통합 `merge_recent`는 legacy, DAG 미사용)

**Silver 테이블 (`processed_events`)**
```
event_id, event_date(파티션), uid, campaign, click, conversion,
conversion_delay_sec, cost, updated_at
```
- `PARTITIONED BY (event_date)`, `format-version=2`, **MOR**(write.*.mode=merge-on-read), `target-file-size=128MB`

**최종 데이터셋 예시 (event_id당 한 행)**
```
event_id | event_date | click | conversion | conversion_delay_sec | cost
E7       | day1       |  1    |    1       | 259200(3일)          | 0.5
E9       | day1       |  1    |    0       | null                 | 0.5
```

**설계**
- **정합성(멱등)**: at-least-once로 중복이 불가피 → 한 곳에서 못 막으니 단계로 나눠 흡수.
  - checkpoint(offset): 유실 방지(단 경계 중복은 남음)
  - dedup(ingest_ts 최신 1건): 소스를 event_id 유일하게 → **MERGE가 깨지지 않게 하는 전처리**
    - (중복 소스로 MERGE하면 타깃 1행에 여러 소스 매칭 → cardinality 에러, 또는 미매칭 중복 INSERT)
  - event_id MERGE: 없으면 INSERT·있으면 UPDATE → **재처리해도 결과 동일(멱등)**
- **INSERT/UPDATE 태스크 분리**: 성능이 아니라 **관측성** 목적(Airflow에서 신규 유입·지연 도착 따로 보고 실패한 쪽만 재시도). 냉정히는 조회를 두 번 하니 성능상 통합 MERGE가 더 나을 수 있음 — 규모·시연 맥락의 선택.
- **파티션 = 노출 시각 고정**: 늦은 클릭·전환이 자기 날짜로 새 행을 만들지 않고 노출 행을 찾아 합쳐짐.

---

## 3. Gold 집계 — `ad_lakehouse_gold` DAG (매시간)

- `processed_to_campaign_summary.py`: Silver → **campaign_summary**(캠페인×날짜로 CTR·CVR·CPA 집계). insert/update 분리 + compact/expire/orphan 동일 구조.
- Gold도 compaction 돌지만 `target-file-size` 미설정 → **기본값(~512MB)**. 128MB는 Silver만.

---

## 4. 조회 / 운영

- **조회**: Athena(쿼리, Trino 기반) · QuickSight(대시보드). 신선도 요구 1시간 → 실시간 스트리밍 대신 마이크로배치.
- **유지보수(매시간 배치에 포함)**: `rewrite_data_files`(compaction) · `rewrite_position_deletes`(MOR delete 정리) · `expire_snapshots`(보존 7일·retain 10) · `remove_orphan_files`(일요일).
- **비용 최적화**: 스몰파일 128MB 병합 + **event_date 파티션 프루닝 + Parquet 컬럼/파일 통계(min/max)** 로 스캔 제외. 프루닝은 Iceberg가 제공, 병합으로 파일을 정돈해 통계가 또렷해야 잘 먹힘.

---

## 5. 핵심 설계 결정 (관점별)

| 관점 | 결정 | 근거 |
|---|---|---|
| **확장성** | Bronze 파티션 = 수집 시각 | 지연 데이터도 재적재 없이 append, 증분 읽기의 발판 |
| **비용 최적화** | 스몰파일 128MB 병합 + 프루닝 | 조회 시 LIST·GET·파싱은 파일 수 비례 → 파일 수↓ |
| **정합성** | checkpoint→dedup→event_id MERGE 멱등 | at-least-once 중복을 단계로 흡수, 재처리 안전 |
| 저장 모드 | MOR | 지연 전환으로 같은 파티션 잦은 UPDATE → CoW는 재작성 부담 |
| 테이블 포맷 | Iceberg | 파티션 에볼루션·ACID MERGE·엔진 호환·벤더락인 회피 |

## 6. 한계·개선점 (정직하게)

1. **Silver/Gold가 raw 전체를 매시간 재읽기** — 증분 아님. Silver 정제엔 체크포인트 없음(스트리밍만 있음). 규모 커지면 비싸짐 → 수집 시각 파티션 기반 증분 읽기로 전환 필요.
2. **merge window 7일 vs 어트리뷰션 30일** — 7일 넘긴 지연 전환은 매시간 경로로 반영 안 됨. → 하루 1회 30일 백필 배치로 보완(설계 방향).
3. **INSERT/UPDATE 분리** — 성능 이득 없음(조회 2회). 관측성/시연 목적. 규모에 따라 통합 MERGE가 나을 수 있음.
4. **스트리밍 배치 크기 상한(maxOffsetsPerTrigger) 미설정** — 트래픽 급증 시 백프레셔 없음.
5. **실측 성능 지표 없음** — 랩 규모. 성과는 "측정 시 이 지표" 형태로만.
6. **exactly-once 아님** — at-least-once 기본 위에서 dedup+MERGE로 정확성 확보(멱등 흡수 방식).

---

## 7. 데이터 흐름 요약 (한 줄)

> Bronze는 수집 시각으로 원본을 관대하게 받고(유실만 방지), Silver가 매시간 raw를 dedup(event_id 최신1건)→LEFT JOIN(노출 base)→event_id MERGE로 event_id당 한 행으로 정합·멱등하게 만들며, 스몰파일 병합·프루닝으로 조회 비용을 낮추고, Gold가 캠페인×날짜 지표로 집계해 Athena/QuickSight로 조회한다.
